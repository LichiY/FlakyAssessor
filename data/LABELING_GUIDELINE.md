# Labeling Guideline for Flaky Test Patch Correctness Assessment

## 1. Overview

This document describes the labeling protocol used to assess the correctness of patches generated by automated flaky repair (AFR) tools. Three annotators independently label each patch as **correct** or **incorrect**, following the criteria and procedures described below.

## 2. Annotator Qualifications

Annotators should have research experience in software testing and be familiar with common flaky test root causes (e.g., nondeterministic collection ordering, asynchronous timing, environment dependencies) and Java testing frameworks (JUnit, AssertJ, Hamcrest).

## 3. Labeling Criteria

A patch is labeled **correct** if and only if it satisfies both of the following criteria:

- **Criterion 1: Absence of Flakiness.** The patched test must eliminate the known source of nondeterminism. The test should produce deterministic outcomes across executions.

- **Criterion 2: Conformance to Test Functionality.** The patched test must preserve the original test's verification intent. The core assertion logic and the scope of behavior being tested must remain consistent with the original test.

A patch that fails either criterion is labeled **incorrect**.

## 4. Incorrect Patch Categories

Incorrect patches are further classified into three types:

### C1: Still Flaky
The patch fails Criterion 1. The patched test still contains a source of nondeterminism and may produce inconsistent results.

**Example indicators:**
- The patch retains use of unordered collections (e.g., `HashMap`, `HashSet`) where element order affects assertions.
- The patch uses `String.contains()` or string comparison for JSON output, which is sensitive to field ordering.
- The patch applies `assertJSONEquals` with underlying string operations that remain order-dependent.

**Example reason:** *"The patch switches to `containsExactlyInAnyOrderElementsOf()` for assertion, but it still requires an exact match and does not solve the ordering problem."*

### C2: Logic Change
The patch fails Criterion 2 but satisfies Criterion 1. The test no longer exhibits flaky behavior, but the verification logic has been altered in a way that changes what the test validates.

**Example indicators:**
- The patch removes key field checks (e.g., timestamp verification) from assertions.
- The patch replaces business logic validation with unrelated utility testing.
- The patch manually constructs expected output, bypassing the real logic under test.
- The patch switches serialization formats (e.g., Protobuf to JSON), changing the original test scope.

**Example reason:** *"The patch only verifies the basic JSON structure and does not cover binary parsing or conversion logic, which changes the test logic."*

### C3: Still Flaky and Logic Change
The patch fails both Criterion 1 and Criterion 2. It retains nondeterminism and alters the original verification logic.

**Example indicators:**
- The patch keeps fragile string matching and simultaneously alters assertion logic.
- The patch is sensitive to JSON field order and improperly expands allowed output states.

**Example reason:** *"1. The patch still uses `contains(gen1, gen2)`, which requires strict order matching and does not solve the ordering issue. 2. It changes the grouping order, which changes the original logic."*

## 5. Labeling Procedure

### Step 1: Identify Root Cause
For each flaky test, the annotator reviews the corresponding developer-submitted pull request (PR) to identify the root cause of the original flakiness.

### Step 2: Assess the Patch
With the root cause established, the annotator evaluates the tool-generated patch against both criteria:
- Does the patch eliminate the identified source of nondeterminism? (Criterion 1)
- Does the patch preserve the original test's verification intent? (Criterion 2)

### Step 3: Assign Label and Category
- If both criteria are satisfied: label as **correct**.
- If Criterion 1 fails: label as **incorrect**, type **C1**.
- If Criterion 2 fails: label as **incorrect**, type **C2**.
- If both criteria fail: label as **incorrect**, type **C3**.

### Step 4: Document Reasoning
For each incorrect patch, the annotator provides a brief reason explaining which criterion failed and why. This reasoning is recorded in the `incorrect_reason` field of the dataset.

## 6. Conflict Resolution

After independent labeling, the three annotators compare their labels. Disagreements are resolved through group discussion until consensus is reached. This process involves multiple rounds of validation and refinement.

## 7. Dataset Fields

| Field | Description |
|---|---|
| `flaky_code` | Original flaky test code |
| `generated_patch` / `fixed_code` | Patched test code (tool-generated or developer-submitted) |
| `isCorrect` | Correctness label (1 = correct, 0 = incorrect) |
| `incorrect_type` | Category of incorrect patch: `rerun` (C1), `semantic` (C2), `rerun.semantic` (C3) |
| `incorrect_reason` | Annotator's reasoning for incorrect label |
| `pr_link` | Link to the developer-submitted pull request |
